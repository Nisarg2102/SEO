# Vercel Services Configuration Report

## 1. Exact Cause of the Error
Vercel returned the error: `"The top-level property functions cannot be used with services because the owning service is ambiguous. Move it under the relevant service."`
In Vercel's unified Services model, `functions` properties (like configuring serverless runtime bounds, timeouts, etc.) must be scoped to the specific service they apply to, rather than existing globally. This ensures Vercel knows exactly which backend or frontend service receives the configuration.

## 2. Exact Configuration Change
Moved the `functions` block into the `"api"` service block inside `vercel.json`. 

* **Why `**/*.ts` was too broad:** While it technically works, it applies the 60-second limit to *every* TypeScript file that Vercel might theoretically parse as a serverless function. 
* **Why `src/main.ts` is now used:** Vercel's zero-config Node.js builder parses `@nestjs/core` and specifically bundles `src/main.ts` into a single Serverless Function. Targeting `src/main.ts` is the precise, officially recommended pattern for NestJS Vercel configurations.

Additionally, `*.tsbuildinfo` was added to `.gitignore`.
* **Why `*.tsbuildinfo` is ignored:** This file is a local incremental cache generated by the TypeScript compiler (`tsc`). It should never be tracked in Git because it causes merge conflicts and pollution between environments.

## 3. Final Service Structure & Architecture
```json
{
  "services": {
    "api": {
      "root": "apps/api",
      "functions": {
        "src/main.ts": {
          "maxDuration": 60
        }
      }
    },
    "web": {
      "root": "apps/web"
    }
  },
  "rewrites": [
    {
      "source": "/api/(.*)",
      "destination": {
        "service": "api"
      }
    },
    {
      "source": "/(.*)",
      "destination": {
        "service": "web"
      }
    }
  ]
}
```
**Architecture Summary:**
* **ONE Vercel Services project** handling both the frontend and backend.
* **`apps/api` -> `api` service:** Configured with a 60-second timeout strictly attached to its `src/main.ts` NestJS entry point.
* **`apps/web` -> `web` service:** Next.js application.
* **Routing:** `/(.*)` goes to Next.js; `/api/(.*)` natively forwards to NestJS.

## 4. Functions Configuration & maxDuration
- **Moved, NOT removed:** The `maxDuration: 60` configuration is absolutely required because AI Agent calls to OpenAI will often exceed the Vercel Hobby/Pro default of 10s or 15s.
- **Location:** Placed strictly on `src/main.ts` inside the `api` service.

## 5. Environment Variables
* `NEXT_PUBLIC_API_URL` finding: Since frontend requests to `/api/*` are perfectly proxied to the NestJS API on the same domain (thanks to the Vercel Services rewrite), client-side browser requests actually don't require an absolute URL. *However*, we kept it intact for now because React Server Components (which execute server-side) still require absolute hostnames.
* All existing variables (`DATABASE_URL`, `DIRECT_URL`, `JWT_SECRET`, `QSTASH_*`) remain required.

## 6. Remaining Vercel Configuration Steps
With the structural ambiguity resolved and precise targeting applied, you can:
1. Commit the project so Vercel picks up the finalized `vercel.json` and `.gitignore`.
2. Vercel will now properly route the services and attach the 60-second limit exactly to the NestJS Serverless Function.
3. Deploy!
